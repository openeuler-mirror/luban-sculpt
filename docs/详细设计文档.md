## 2. 系统与数据流

**定位**：硬件感知的多后端 PTQ 编排。单阶段执行中枢为 `BackendPlan`。

```
Recipe + Profile
  → HAE → HwDecision, ProbeResult
  → compile → BackendPlan
  → validate_quant_capability（压前）
  → Backend.quantize（含 CalibRunner）
  → HAL + build_manifest → manifest.json
  → [可选] validate_quantized_model（压后）
```

产物目录约定：每阶段写入 `output_subdir`（默认 `stage_{i}_{backend}`）；根目录写 `pipeline_manifest.json`。

## 3. 契约层（IR）

**核心功能**：层间传递的结构化数据（Pydantic），Backend / Gate / HAL / Export 只认这些类型。

### 3.1 关键类型

| 类型 | 核心功能 |
|------|----------|
| `HwDecision` | HAE 输出的硬件决策（profile、融合、编码、布局、拓扑） |
| `ProbeResult` | 算子/能力探测是否通过 |
| `QuantIntent` | 编译后的量化意图（模型、backend、scheme、ignore、calib、options） |
| `BackendPlan` | **阶段执行中枢** = Intent + HwDecision + ExportFormat |
| `ArtifactManifest` | 落盘 `manifest.json` 对账信息 |
| `QuantizedArtifact` | 阶段产物句柄：`output_dir` + `manifest` |

### 3.2 字段摘要

**`QuantIntent`**

| 字段 | 含义 |
|------|------|
| `model_id` | 模型路径或 HF id |
| `backend` | 后端名（llm_compressor / gptq / msmodelslim …） |
| `abstract_scheme` | 抽象量化方案（如 fp8_dynamic、ascend_w8a8） |
| `deploy_target` | 部署目标（vllm_cuda / vllm_ascend …） |
| `arch_snapshot` | ModelArch 快照 |
| `ignore` | 不量化模块名列表 |
| `calib` | 校准配置 dict（交给 CalibRunner） |
| `backend_options` | 后端私有参数 |

**`BackendPlan`**：`intent` + `hw` + `export_format`。

**`ExportFormat`（枚举）**：`compressed-tensors` / `awq_hf` / `gptq_hf` / `fp8_hf` / `vllm_ascend` / `infera-v1`。

**`ArtifactManifest.write_json(out_dir)`**：写入 `out_dir/manifest.json`，返回路径。

## 4. Pipeline 编配

**核心功能**：编排 HAE → 多阶段 Backend → 可选压后校验；解析单 `quant` 与多 `pipeline.stages`。

### 4.1 `QuantPipeline`

```python
QuantPipeline(
    profile_name: str = "auto",
    *,
    router: BackendRouter | None = None,
    hae: HardwareAwareEngine | None = None,
    stages: Sequence[PipelineStage] | None = None,
    validate_quantized_model: bool = False,
    validate_runtime: bool = False,
    runtime_mode: RuntimeMode = "import",
)
```

| 参数 | 说明 |
|------|------|
| `profile_name` | Profile id，或 `"auto"` 由 HAE 解析 |
| `router` | Backend 路由；默认新建 `BackendRouter` |
| `hae` | 硬件引擎；默认按 profile 新建 |
| `stages` | 若传入则**完全替换**默认阶段链 |
| `validate_quantized_model` | 是否追加压后 HF 校验阶段 |
| `validate_runtime` | 压后是否再跑 vLLM runtime（需上一开关为真） |
| `runtime_mode` | `"import"` \| `"load"` \| `"generate"` |

默认阶段：`HAEStage` → `BackendComposeStage`（+ 可选 `QuantizedModelValidateStage`）。

```python
run(recipe_path: Path, output_dir: Path) -> QuantizedArtifact
```

| 参数 | 说明 |
|------|------|
| `recipe_path` | Recipe YAML 路径 |
| `output_dir` | 流水线输出根目录 |
| **返回** | **最后一阶段**的 `QuantizedArtifact` |

```python
run_recipe(
    recipe: dict,
    output_dir: Path,
    *,
    recipe_path: Path | None = None,
) -> QuantizedArtifact
```

| 参数 | 说明 |
|------|------|
| `recipe` | 已加载的 recipe dict |
| `output_dir` | 输出根目录 |
| `recipe_path` | 可选，仅用于日志 |

### 4.2 阶段配置

**`QuantStageConfig`**

| 字段 | 说明 |
|------|------|
| `name` | 阶段名 |
| `backend` | 后端 entry 名 |
| `algorithm` | 可选；写入 `backend_options.algo` |
| `abstract_scheme` / `deploy_target` / `ignore` | 可选覆盖 |
| `backend_options` | 与 recipe 中 `quant.<backend>` 合并（本字段优先） |
| `input_from` | `"recipe"`：用原始 model_id；`"previous"`：上一阶段 `output_dir` |
| `output_subdir` | 相对根目录的子目录；默认 `stage_{i}_{backend}` |
| `enabled` | 是否启用 |

**`PipelineConfig`**：`stages: list[QuantStageConfig]`；`enabled_stages()` 返回启用列表。

### 4.3 编配辅助

```python
parse_pipeline_config(recipe: dict[str, Any]) -> PipelineConfig
```

从 recipe 解析阶段列表。优先级：`pipeline.stages` → `pipeline` 列表 → 兼容顶层 `quant`（单阶段）。

```python
build_stage_recipe(
    base: dict[str, Any],
    stage: QuantStageConfig,
    *,
    model_id: str | None = None,
) -> dict[str, Any]
```

| 参数 | 说明 |
|------|------|
| `base` | 完整 recipe |
| `stage` | 当前阶段配置 |
| `model_id` | 覆盖本阶段模型路径（如 previous 产物目录） |
| **返回** | 可供 `compile_recipe` 使用的单阶段 recipe 视图 |

### 4.4 阶段协议

```python
class PipelineStage(ABC):
    name: str
    def run(self, ctx: PipelineContext) -> PipelineContext: ...
```

| 内置阶段 | 核心功能 |
|----------|----------|
| `HAEStage` | 探测硬件，写入 `ctx.hw` / `probe` / `profile` |
| `BackendComposeStage` | 逐阶段 compile → Gate → `quantize` → 写 sidecar |
| `QuantizedModelValidateStage` | 对最后产物做 `validate_quantized_model` |

`PipelineContext` 承载 recipe、输出根、profile、各 `StageResult`；`last_artifact` 取最后阶段产物。

## 5. Compiler

**核心功能**：Recipe + 硬件决策 + Profile → `BackendPlan`（含 ModelArch 合并、export 选择）。

```python
load_recipe_yaml(path: Path) -> dict[str, Any]
```

读取 recipe YAML。

```python
compile_recipe(
    recipe: dict[str, Any],
    hw: HwDecision,
    profile: dict[str, Any],
) -> BackendPlan
```

| 参数 | 说明 |
|------|------|
| `recipe` | 含 `model_id` / `quant` / `calib` 的 dict |
| `hw` | HAE 产出的硬件决策 |
| `profile` | Profile 模板 dict |
| **返回** | 组装好的 `BackendPlan` |

编译期内完成：架构决议、ignore 合并、MoE 校准样本放大、`backend_options` 注入、`export_format` 选择。

```python
compile_plan(recipe_path: Path | str, profile_name: str) -> BackendPlan
```

| 参数 | 说明 |
|------|------|
| `recipe_path` | Recipe 路径 |
| `profile_name` | Profile id |
| **返回** | 便捷封装：内部完成 HAE 决策 + `compile_recipe` |

## 6. ModelArch

**核心功能**：识别模型架构并给出量化策略（ignore、MoE 提示、偏好算法），与硬件 Profile **正交**——芯片相关逻辑不进本模块。

### 6.1 架构取值

**Dense**

`llama` · `qwen` · `deepseek` · `mistral` · `chatglm` · `gemma` · `dense_generic` · `unknown`  
（baichuan / yi / phi / internlm 等常回落 `dense_generic`；多模态用 `is_multimodal`，不单开 arch）

**MoE**（属 `MOE_ARCHES`）

`qwen_moe` · `deepseek_moe` · `mixtral` · `moe_generic`

枚举全部策略：`luban-sculpt model-arches` → `list_arches()`。

### 6.2 关键接口

```python
resolve_model_arch(
    model_id: str,
    *,
    recipe: dict | None = None,
    hf_config: dict | None = None,
) -> ModelArchSnapshot
```

| 参数 | 说明 |
|------|------|
| `model_id` | 模型路径或仓库 id |
| `recipe` | 可选；含 `model_arch` / `model.arch` 时优先 |
| `hf_config` | 可选；已加载的 HF config |
| **返回** | 架构快照（见下） |

**分类顺序**

1. Recipe：`model_arch` / `model.arch`  
2. `hf_config` 或本地 `model_id/config.json`（`model_type` / `architectures`）  
3. `model_id` 字符串启发式  
4. `UNKNOWN`  

匹配时 **先 MoE 规则、再 Dense 规则**，避免 `qwen` 误吃掉 `qwen_moe`。

**`ModelArchSnapshot` 字段**

| 字段 | 说明 |
|------|------|
| `arch` | `ModelArch` 枚举 |
| `is_moe` | 是否 MoE（`MOE_ARCHES` 或 recipe 标记） |
| `is_multimodal` | 是否多模态 / VL |
| `hf_model_type` / `architectures` | 来自 HF config 的原始信息 |
| `source` | `recipe` \| `hf_config` \| `heuristic` \| `unknown` |
| `quant_hints` | 来自 `ArchQuantPolicy`（及 VL 附加 hint） |

```python
merge_ignore_list(
    recipe_ignore: list[str] | None,
    arch: ModelArch,
    *,
    is_multimodal: bool = False,
) -> list[str]
```

| 参数 | 说明 |
|------|------|
| `recipe_ignore` | Recipe 中的 ignore |
| `arch` | 已决议架构 |
| `is_multimodal` | 为真时追加 VL 相关 ignore |
| **返回** | recipe ∪ policy.default_ignore（∪ VL extras），去重保序 |

```python
apply_arch_to_backend_options(
    backend: str,
    options: dict[str, Any],
    model: ModelArchSnapshot,
) -> dict[str, Any]
```

| 参数 | 说明 |
|------|------|
| `backend` | 当前 backend 名 |
| `options` | 原 `backend_options` |
| `model` | 架构快照 |
| **返回** | 非破坏注入：`model_arch` / `is_moe` / `is_multimodal`；msmodelslim 可补 `model_type` hint |

```python
list_arches() -> list[dict[str, Any]]
```

返回各 arch 的策略摘要（先 MoE 后 Dense），供 CLI 使用。

### 6.3 ArchQuantPolicy

每个 `ModelArch` 一条静态策略：

| 字段 | 含义 | 示例 |
|------|------|------|
| `default_ignore` | 默认不量化模块 | Qwen：`lm_head`、`re:.*mlp.gate$` |
| `quant_hints` | 编译期提示 | MoE：`calib_samples_factor`；Ascend：`msmodelslim_model_type` |
| `notes` | 说明文字 | — |

`is_moe` / `is_multimodal` **不在** Policy 上，而在 Snapshot / `MOE_ARCHES`。

**编译期行为（由 Compiler 调用）**

- `ignore` = recipe.ignore ∪ policy.default_ignore（∪ VL extras）  
- MoE：`calib.max_samples *= calib_samples_factor`（来自 snapshot.quant_hints）  
- `backend_options` 写入 arch 相关字段  
- manifest 记录 `model_arch` / `model_arch_snapshot`

### 6.4 Recipe 示例

```yaml
model_id: /data/models/Qwen2.5-7B-Instruct
model_arch: qwen                 # 推荐显式写出
quant:
  backend: gptq
  abstract_scheme: hygon_w8a8_gptq
  ignore:
    - lm_head                    # 与策略 default_ignore 合并
calib:
  max_samples: 128
```

MoE：

```yaml
model_id: Qwen/Qwen3-MoE-Stub
model_arch: qwen_moe
quant:
  backend: llm_compressor
  abstract_scheme: w4a16_g32
calib:
  max_samples: 256               # 若 factor=2.0，编译后变为 512
```

### 6.5 扩展方式

**新 Dense 架构**

1. `ModelArch` 增加枚举成员（若需要）  
2. 注册对应 `ArchQuantPolicy`（default_ignore / quant_hints）  
3. 增加 HF `model_type` / `architectures` / `model_id` 匹配规则  

**新 MoE 架构**

同上，并加入 `MOE_ARCHES`。

**不要**把 SoC / CANN / DTK 等芯片逻辑写进 ModelArch——那属于 Profile 与 HAE。

## 7. HAE

**核心功能**：探测硬件、匹配 Profile、算子 probe、合成 `HwDecision`。

```python
HardwareAwareEngine(
    profile_name: str = "auto",
    *,
    enable_real_probe: bool = True,
    fallback_on_probe_failure: bool = True,
)
```

| 参数 | 说明 |
|------|------|
| `profile_name` | 初始/默认 profile |
| `enable_real_probe` | 是否执行 probe |
| `fallback_on_probe_failure` | probe 失败时是否降级为 `ok=True, degraded=True` |

```python
run(profile_name: str | None = None) -> tuple[HwDecision, ProbeResult, dict]
```

| 参数 | 说明 |
|------|------|
| `profile_name` | 本次强制 profile；`None` 则自动解析 |
| **返回** | `(硬件决策, 探测结果, profile 模板 dict)` |

其它常用方法：`detect()`、`probe(profile)`、`resolve_profile_name(...)`、`synthesize_decision(...)`。

能力查表：`lookup_device_caps(device_name, vendor)`、`match_profile_id(device_name)`、`build_hardware_capability(...)`。

## 8. HAL / Export

### 8.1 HAL

**核心功能**：按 `HwDecision` 选择校准 kernel 名、做 encoding/layout 标记与 repack（当前多为 stub，接口已稳定）。

```python
HALPipeline(hw: HwDecision)
```

| 方法 | 说明 |
|------|------|
| `select_calib_kernel() -> str` | 返回融合/通用 kernel 名 |
| `calib_forward(layer_name, tensor) -> Any` | 校准前向占位 |
| `encoding_adaptor(weights) -> dict` | FP8 等编码适配标记 |
| `layout_transform(weights) -> dict` | 权重布局变换标记 |
| `plan_distributed_calib(world_size) -> dict` | 分布式校准计划 |
| `repack_for_save(weights) -> dict` | 串联 encoding + layout，供落盘 |

统一出口（Backend 调用）：

```python
run_with_hal(
    plan: BackendPlan,
    output_dir: Path,
    weights_stub: dict,
) -> QuantizedArtifact
```

| 参数 | 说明 |
|------|------|
| `plan` | 当前阶段计划 |
| `output_dir` | 阶段输出目录 |
| `weights_stub` | 权重元数据/占位（dry-run 亦适用） |
| **返回** | 含 `manifest.json` 的产物句柄 |

### 8.2 Export

```python
build_manifest(plan: BackendPlan, repack_log: list[str]) -> ArtifactManifest
```

| 参数 | 说明 |
|------|------|
| `plan` | 阶段计划 |
| `repack_log` | HAL 记录的 repack 步骤 |
| **返回** | 含 `vllm_launch` 等对账字段的 manifest |

## 9. Calib

**核心功能**：全 Backend 共用的校准数据入口；不内置磁盘数据集。

### 9.1 `CalibRunner`

```python
CalibRunner(plan: BackendPlan, forward_fn: Callable | None = None)
```

| 参数 | 说明 |
|------|------|
| `plan` | 从 `plan.intent.calib` 读配置 |
| `forward_fn` | 可选；`run()` 时逐样本调用 |

**calib 常用键**：`source`（默认 `stub`）、`max_samples`、`batch_size`、`split`、`text_column`、`distributed` / `world_size`。

```python
load() -> CalibData
```

物化 `samples` / `texts` 与 `report`。分布式 stub 时样本为空。

```python
oneshot_kwargs() -> dict[str, Any]
```

给 llmcompressor oneshot：`dataset`、`num_calibration_samples`（`stub` 不传 dataset）。

```python
write_jsonl(path: Path, data: CalibData | None = None) -> Path
```

写出每行含 `text` 的 jsonl。

```python
resolve_calib_file(
    output_dir: Path,
    data: CalibData | None = None,
    *,
    explicit: str | Path | None = None,
) -> Path | None
```

| 参数 | 说明 |
|------|------|
| `explicit` | 显式文件路径优先 |
| 否则 | `source` 若为已存在文件则用之；否则物化 `luban_calib.jsonl` |

### 9.2 样本迭代

```python
iter_text_samples(
    source: str,
    *,
    max_samples: int = 512,
    split: str = "train",

```

| `source` | 行为 |
|----------|------|
| `"stub"` | 内存造最多 8 条假样本 |
| 其它 | 按 HF dataset id 加载；失败回退 stub |

## 10. Backend

**核心功能**：插件化执行量化；只消费 `BackendPlan`，不做硬件探测与架构分类。

### 10.1 插件协议

```python
class QuantBackend(ABC):
    name: str
    def quantize(self, plan: BackendPlan, output_dir: str) -> QuantizedArtifact: ...
```

| 参数 | 说明 |
|------|------|
| `plan` | 阶段执行计划 |
| `output_dir` | 本阶段输出目录 |
| **返回** | 产物目录 + manifest |

```python
BackendRouter(registry: BackendRegistry | None = None)
BackendRouter.run(plan: BackendPlan, output_dir: str) -> QuantizedArtifact
```

按 `plan.intent.backend` 路由到已注册插件。`BackendRegistry.registered() -> list[str]` 列出名称。

### 10.2 已注册后端（能力）

| 名称 | 核心功能 | 备注 |
|------|----------|------|
| `llm_compressor` | oneshot PTQ + Modifier 链 | 支持 Dry-Run 脚本 |
| `gptq` | GPTQModel 量化 | 支持 Dry-Run |
| `msmodelslim` | 调用 `msmodelslim quant` CLI | 支持 Dry-Run `.sh` + calib sidecar |
| `awq` | 占位落盘 | stub |
| `custom` | 自定义占位 | stub |

各实装 runner 对外习惯入口（供 SDK 直接调用时）：

```python
run_llm_compressor_oneshot(plan, output_dir, *, dry_run=None) -> dict
run_gptqmodel_quantize(plan, output_dir, *, dry_run=None) -> dict
run_msmodelslim_quant(plan, output_dir, *, dry_run=None) -> dict
```

| 参数 | 说明 |
|------|------|
| `plan` | `BackendPlan` |
| `output_dir` | 输出目录 |
| `dry_run` | `None` 时看对应 `LUBAN_*_DRY_RUN` 环境变量 |

## 11. Validate

**核心功能**：两条校验轴——**压前能力门禁**与**压后产物校验**。

### 11.1 压前

```python
validate_quant_capability(
    plan: BackendPlan,
    profile: dict[str, Any],
    probe: ProbeResult,
) -> None
```

| 参数 | 说明 |
|------|------|
| `plan` | 待执行计划 |
| `profile` | Profile 模板 |
| `probe` | HAE 探测结果 |
| **异常** | `QuantCapabilityError`：probe/scheme/backend/deploy/FP8 能力不匹配 |

内部会调用 `validate_intent_profile(intent, hw, profile, probe)`。

### 11.2 压后

```python
validate_hf_config(
    model_path: Path,
    *,
    plan: BackendPlan | None = None,
) -> list[str]
```

| 参数 | 说明 |
|------|------|
| `model_path` | 量化模型目录 |

## 13. 配置约定与 Dry-Run

### 13.1 Recipe（逻辑字段）

| 字段 | 含义 |
|------|------|
| `model_id` | 模型 |
| `model_arch` | 可选架构覆盖 |
| `quant.backend` / `abstract_scheme` / `deploy_target` / `ignore` | 量化意图 |
| `quant.<backend>` | 进入 `backend_options` |
| `calib.*` | 进入 `QuantIntent.calib` |
| `pipeline.stages[]` | 多阶段编配（见 §4.2） |

### 13.2 Profile（逻辑字段）

vendor、schemes、enabled backends、`hw_defaults`、`required_ops_probe`、能力数字等；由 HAE 加载并参与 Gate。

### 13.3 Dry-Run

| 环境变量 | 作用 |
|----------|------|
| `LUBAN_LLM_COMPRESSOR_DRY_RUN=1` | llm_compressor 只写脚本/stub |
| `LUBAN_GPTQMODEL_DRY_RUN=1` | gptq 只写 stub |
| `LUBAN_MSMODELSLIM_DRY_RUN=1` | msmodelslim 只写 command.sh |

工具未安装时行为等同 Dry-Run；**均仍写 `manifest.json`**。

典型 sidecar：oneshot 脚本、`quant_stub.json`、`msmodelslim_command.sh`、`luban_calib.jsonl`、`quantized_model_validate.json`。

### 13.4 已知限制（接口层）

- HAL encoding/layout/calib_forward 为 stub 实现  
- `awq` / `custom` 后端为占位  
- 多阶段以目录串联为主，权重级 handoff 仍偏骨架  
- `iter_text_samples` 对本地 jsonl 无专用解析（文件路径经 `resolve_calib_file` 处理）
